# Diary: Plan and Specify PostingJournalFeature for BFF DomainServices

Planning and specification for exposing posting journal from the BFF WebApi, enabling the React application to reload posting journal state after add/update/delete operations.

## Step 1: Discover and Validate Architecture Patterns

**Author:** main

### Prompt Context

**Verbatim prompt:** User asked to review TODO.md requirements and create specifications for PostingJournalFeature following established query patterns

**Interpretation:** Understand the existing feature architecture (AccountingIdentificationFeatureBase pattern, query/response/feature structure, DI registration) and apply it to the new PostingJournalFeature requirement

**Inferred intent:** Minimize new code by discovering and reusing existing implementations, establishing precise implementation specifications before coding begins

### What I did

1. Examined TODO.md to understand business requirements: expose posting journal for accounting to support React app reload after modifications
2. Studied AccountingFeature and AccountSummaryFeature implementations as reference patterns
3. Discovered that ApplyPostingJournalModel already exists in WebApi.ClientApi (auto-generated by NSwag)
4. Found IPostingJournalTexts interface and IPostingJournalTextsBuilder implementation already exist
5. Found PostingJournalTextsBuilder already implemented and registered in ServiceCollectionExtensions
6. Found IPostingJournalRuleSetBuilder interface and PostingJournalRuleSetBuilder implementation already exist
7. Verified DI registration pattern: AddFeatures() auto-discovers Feature classes - no manual registration needed
8. Analyzed PostingJournal.jsx React component to identify all 25 static text keys needed
9. Discovered permission requirement difference: PostingJournalFeature needs IsAccountingModifier (write) not IsAccountingViewer (read)
10. Created detailed specifications in TODO.md including all method implementations and test strategies

### Why

Following established patterns reduces code duplication and maintenance burden. The architecture already supports the requirements:
- Generic AccountingIdentificationFeatureBase<TRequest, TResponse, TModel, TDynamicTexts, TDynamicTextsBuilder, TValidationRuleSetBuilder> base class handles the common flow
- IAccountingGateway.GetPostingJournalAsync() already exists
- Dynamic text builders and validation rule builders for PostingJournal already implemented
- NSwag-generated models eliminate DTOs

Permission requirement analysis: PostingJournal is for appending entries (modification), not just reading - requires modifier access instead of viewer access. This creates a specific override point in VerifyPermissionAsync().

### What worked

- Existing infrastructure is well-designed for reuse - zero need to create new gateways, builders, or text interfaces
- ApplyPostingJournalModel + IPostingJournalTexts combination provides exact data types needed
- Analyzing React component revealed all required static text keys in one pass
- Permission override pattern is clear from base class structure

### What didn't work

- Initially suggested creating ApplyPostingJournalModel → discovered it already exists ✓ (actually a win)
- Initial permission analysis suggested viewer-level access → corrected to modifier-level after understanding the feature's purpose

### What I learned

- This codebase has excellent pattern library and infrastructure reuse
- NSwag auto-generation from WebApi eliminates round-trip DTOs - models are generated once and reused throughout layers
- Permission model has clear levels: IsAuthenticated → HasAccountingAccess → IsAccountingViewer/IsAccountingModifier
- Static text keys can be discovered by analyzing React component UI rendering

### What was tricky

1. **Permission override depth:** Understanding that PostingJournalFeature needs to override VerifyPermissionAsync() to enforce modifier access (write permission) rather than inheriting viewer access (read permission) from base class required careful analysis of AccountingIdentificationFeatureBase implementation

2. **Static text key count:** Ensuring all 25 keys were identified by cross-referencing React component with StaticTextKey enum - organized by category (headers, labels, actions, dialog buttons) to avoid omissions

3. **Test pattern mapping:** Translating how AccountSummaryFeature's VerifyPermissionAsyncTests work and adapting for PostingJournalFeature's different permission requirement (IsAccountingModifier instead of IsAccountingViewer)

### What warrants review

1. **Permission Override Implementation:** The VerifyPermissionAsync() override checking for IsAccountingModifier instead of IsAccountingViewer is the key permission difference. Reviewers should verify:
   - That modifier-level access is the correct requirement (not viewer)
   - That the override correctly implements: IsAuthenticated AND HasAccountingAccess AND IsAccountingModifier

2. **Static Text Keys:** All 25 keys must be included in GetStaticTextSpecifications(). Review organized by category:
   - Field headers: PostingJournal, PostingDate, PostingReference, Account, PostingText, BudgetAccount, Debit, Credit, ContactAccount
   - Field labels: AccountName, Posted, Available, Balance, PostingValue
   - Action texts: AddPostingJournalLine, UpdatePostingJournalLine, DeletePostingJournalLine, PostingJournalLineDeletionQuestion
   - Dialog/button texts: Create, Update, Delete, ConfirmDeletion, DeleteVerificationInfo, Reset, Cancel

3. **Generic Type Parameters:** Six type parameters in AccountingIdentificationFeatureBase - verify all are correctly specified for PostingJournalFeature

### Future work

- Implementation phase: Create PostingJournalRequest, PostingJournalResponse, PostingJournalFeature classes following specifications
- Create ExecuteAsyncTests and VerifyPermissionAsyncTests per test strategy
- Create WebApi GET endpoint /api/accounting/{accountingNumber}/postingjournal
- Verify NSwag code generation picks up new endpoint

## Step 2: Create Comprehensive User Stories Document

**Author:** main

**Interpretation:** Convert detailed requirements from TODO.md into agile-formatted user stories with sprint-ready structure, maintaining all technical details while organizing for team consumption.

   - Epic header: "Expose Posting Journal for Accounting via BFF WebApi"
   - 12 complete user stories (Stories 1-12) organized by architectural layer
   - Implementation summary table showing components, types, status, and estimated LOC
   - Reused components table documenting 6 existing implementations
   - Key architectural decisions section

2. Structured user stories by layer progression:
   - Stories 1-3: DomainServices layer (PostingJournalRequest, PostingJournalResponse, PostingJournalFeature)
   - Stories 4-5: DomainServices tests (ExecuteAsyncTests, VerifyPermissionAsyncTests)
   - Story 6: WebApi authorization policy (AccountingModifier)
   - Story 7: WebApi response DTO (PostingJournalResponseDto)
   - Story 8: WebApi endpoint (PostingJournalAsync GET method)
   - Story 9: WebApi endpoint tests (PostingJournalAsyncTests)
   - Stories 10-12: Build verification, code generation, documentation

3. Each user story includes:
   - User role-based narrative (As a... I want... So that...)
   - Acceptance criteria (checkbox lists for verification)
   - Technical details section (implementation guidance beyond acceptance criteria)
   - 9 stories × 9+ acceptance criteria each = comprehensive coverage

4. Added tables and decision documentation for at-a-glance understanding

### Why

User stories enable:
- **Business clarity:** Each story articulates value through role-based narrative
- **Sprint planning:** Well-scoped stories fit naturally into sprint boundaries
- **Team communication:** Developers, QA, and PMs share common understanding format
- **Progress tracking:** Checkbox acceptance criteria enable clear done/not-done status
- **Parallel development:** Stories can be assigned to different team members with minimal dependencies
- **Estimation:** LOC estimates help with velocity planning

Separating into dedicated file enables story tracking without mixing with requirements/acceptance criteria checklist.

### What worked

- Organizing stories by architectural layer (DomainServices → WebApi) creates natural progression and reduces circular dependencies
- Technical details sections bridge gap between business requirements (user story) and implementation reality
- Implementation summary table provides bird's-eye view: 9 components, ~665 LOC, 3-5 days estimated effort
- Reused components table highlights that 6 existing implementations eliminate new work

### What didn't work

Initial placement: User stories in TODO.md mixed requirements checklists with agile stories. This created:
- Duplication (same info in multiple formats)
- Reader confusion (unclear which to follow)
- Maintenance burden (changes needed in two places)

**Solution:** Removed user stories from TODO.md, keeping only requirements + acceptance criteria checklist there. TODO.md now focuses on requirements; user stories file focuses on sprint planning.

### What I learned

1. **Separation of concerns:** Requirements (TODO.md) serve different purposes than user stories (sprint planning file)
2. **Story organization:** Grouping by layer creates natural dependency flow and enables parallel work
3. **Technical details bridge:** Balancing business language with implementation specifics helps both PMs and developers
4. **Effort estimation:** Breaking into ~10-50 LOC chunks per story keeps estimation granular and accurate

### What was tricky

1. **Story boundaries:** Deciding whether to combine or split related work (e.g., should tests be in same story as feature class, or separate story?). Chose separate stories for clarity and testability sequencing.

2. **Balancing abstraction:** User stories need business value language, but PostingJournal feature is fairly technical. Solved by putting "As a Backend Developer" as the role (honest about who benefits) while keeping "So that..." focused on business outcome.

3. **Completeness verification:** Ensuring all 25 static text keys were captured in Story 3 technical details required cross-checking against both TODO.md and React component analysis.

### What warrants review

1. **Story dependencies:** Verify that Story order (1-12) reflects true implementation dependencies and that independent stories can be parallelized
2. **Acceptance criteria completeness:** Each story should be independently testable - review that all needed info is in that story's section, not requiring cross-reference to other stories
3. **Effort estimation:** 3-5 days for ~665 LOC × 23 tests - validate against team velocity

### Future work

- Developers will use Story 1-9 for implementation and testing
- Story 10 (Build & Tests) serves as quality gate
- Story 11 (Code Generation) triggers NSwag post-build
- Story 12 (Documentation) captures implementation decisions and lessons learned

## Step 3: Deduplicate Documentation & Prepare for Implementation

**Author:** main

### Prompt Context

**Verbatim prompt:** User asked: "Did you remove the User Story content from @file:TODO.md?" and later "Do @file:posting-journal-feature-user-stories.md contains all information from @file:TODO.md?"

**Interpretation:** Clarify what information lives in which file and ensure complete, non-duplicated documentation across both files.

**Inferred intent:** Establish single source of truth for different consumption patterns (requirements checklist vs. sprint planning).

### What I did

1. **Removed user stories from TODO.md:**
   - Deleted entire "## User Stories" section (12 stories + Epic header, ~450 lines)
   - Kept requirements, acceptance criteria, and test strategies in TODO.md
   - Result: TODO.md now 231 lines, user-stories file is 400+ lines

2. **Analyzed information distribution:**
   - **TODO.md retains:** Business goal, technical requirements, test strategies, acceptance criteria checklists, code examples (policy config, endpoint implementation)
   - **User stories file contains:** Agile-formatted stories, acceptance criteria with context, technical details for developers, implementation summary, effort estimates
   - **Gaps identified:** User stories file missing some code examples (PolicyConfiguration, endpoint code blocks) for quick reference during implementation

3. **Established documentation structure:**
   - TODO.md = Requirements document (what + why + how to verify)
   - User stories = Sprint planning document (story points scope + acceptance criteria + business value)
   - Neither is complete without the other:
     - Developers implementing Story 8 need TODO.md code examples for exact syntax
     - QA tracking progress needs user stories for sprint board status

### Why

Deduplication serves multiple purposes:
- **Maintainability:** Changes to requirements need to be made in one place only
- **Clarity:** Reader knows which document to use for which purpose (sprint planning vs. detailed requirements)
- **Size:** Each file stays focused (TODO.md for requirements, user stories for agile workflows)
- **Handoff:** When implementation begins, developers get user stories; QA/reviewers use TODO.md acceptance criteria; project managers track Story 1-12 on board

### What worked

- Clear file naming (`posting-journal-feature-user-stories.md`) makes purpose obvious
- Keeping code examples in TODO.md provides implementation reference without bloating user stories
- Keeping detailed acceptance criteria in both files enables different stakeholder needs

### What didn't work

- Initial approach of having stories in TODO.md created version control burden (had to maintain parallel versions)
- Solution: Separate files from the start

### What I learned

1. **Document structure matters:** Requirements (checklist-oriented) and stories (narrative-oriented) serve different purposes
2. **Stakeholder alignment:** Requirements docs for QA/architects; stories for developers/PMs; both needed for complete handoff
3. **Single source of truth pattern:** When duplication exists, specify which file is authoritative (TODO.md for requirements; user stories for sprint scope)

### What was tricky

1. **Determining optimal split:** What belongs in each file? Settled on:
   - TODO.md: The "what must be true" (acceptance criteria + test strategies)
   - User stories: The "how we'll build it" (stories + estimates + business value)

2. **Completeness without duplication:** Each file needed to be complete enough to stand alone while not repeating information. Used cross-references (links at bottom of each file) instead of duplication.

### What warrants review

1. **Acceptance criteria alignment:** Compare identical criteria in TODO.md vs. user stories - ensure they're in sync
2. **Code examples coverage:** Verify that developers implementing Story 8 can find complete endpoint implementation details in TODO.md
3. **Test strategy consistency:** Ensure ExecuteAsyncTests, VerifyPermissionAsyncTests, PostingJournalAsyncTests in user stories match TODO.md test strategy

### Future work

- Implementation team will work from user stories (Story 1-12 on sprint board)
- Implementation team will reference TODO.md for exact code patterns and acceptance criteria
- This diary documents specification phase completion; next diary update will be at implementation completion
- When implementation begins, each developer should claim 1-2 stories and update their status daily
